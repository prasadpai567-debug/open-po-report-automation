# Open PO Report Automation — Application Analysis

## Scope and method

This report is based on static inspection of the supplied `OpenPO_Report_Automation.xlsm` package and inspection of its VBA project in the Excel VBA editor. The workbook was not run against SAP or Outlook because execution would drive a live SAP transaction and create an email draft. The source workbook and its VBA logic were not modified.

## Executive conclusion

The application is a small, focused Excel VBA front end for a recurring procurement report. It accepts a document-date range from two worksheet cells, drives an active SAP GUI session through transaction `ME2N`, exports the resulting open purchase order report to a local `.xlsx` file, and prepares an Outlook email with the exported file attached.

The automation is useful because it standardizes a repeated SAP reporting and email-preparation sequence. It is not a full report-analysis workbook: the workbook itself contains no report table, formulas, charts, PivotTables, or data model. The business report is generated by SAP and saved outside the workbook.

### Main procedure logic

The key logic is:

1. Bind to the worksheet named `Salem Open PO Report`.
2. Read `B2` and `B3` and format them as SAP date strings.
3. Create `C:\TEMP` if needed.
4. Build a filename using the report label and end date.
5. Attach to the first SAP GUI connection and first SAP session.
6. Exit with a message if no active SAP session is available.
7. Open `/NME2N`.
8. Open the saved-variant selection, enter the configured variant, and confirm it.
9. Populate the SAP document-date low and high fields.
10. Execute the report and select the export command.
11. Enter the local folder and filename in the SAP save dialog.
12. Create an Outlook mail item, populate the hard-coded message fields, attach the exported file, and display the draft.
13. Release object references.

## Complete application workflow

### Input

The user enters or updates the document-date range in the two value cells on the worksheet.

### SAP processing

The macro expects SAP GUI for Windows to be open and logged in. It drives the first active session using recorded SAP GUI control IDs. It navigates to `ME2N`, applies the saved variant configured in the workbook, enters the start and end dates, runs the report, and uses the SAP export flow to create an `.xlsx` file.

### File output

The local destination is hard-coded as `C:\TEMP`. The filename includes the report label and the end date. The workbook does not import the generated report back into the worksheet.

### Email preparation

If Outlook automation succeeds, the macro creates a new message, populates recipient and sender-on-behalf fields, adds a standard subject and body, attaches the exported file, and displays the draft. Because `.Display` is used, a user must review and send the message manually. There is no automatic `.Send` call.

## Business benefits

The implementation can provide the following benefits when the SAP and Outlook configuration is stable:

- Fewer repeated SAP navigation steps.
- Consistent use of the intended report transaction and saved variant.
- Reduced manual date-entry and export mistakes.
- Standardized report filename and email message.
- Faster preparation of a recurring procurement communication.
- Human review retained before email delivery.

No time-savings measurement or error-rate comparison is included in the workbook, so quantified improvement claims should not be made without operational evidence.

## Dependencies and setup requirements

### Required software

- Windows desktop Excel with VBA support.
- SAP GUI for Windows with GUI Scripting available.
- Microsoft Outlook desktop for the draft-email step.

### Required configuration

- A logged-in SAP session.
- Access to SAP transaction `ME2N`.
- The configured saved variant available in the target SAP environment.
- Permission to write to `C:\TEMP`.
- A valid Outlook profile and permission to create a draft with an attachment.

The VBA uses late binding for SAP GUI and Outlook, so it does not rely on explicit VBA references to those libraries. The runtime applications are still mandatory.

## Security and confidentiality findings

The supplied workbook should not be published unchanged.

### Findings in workbook metadata

- The file contains personal creator and last-modified-by metadata.
- The file contains company metadata.
- The workbook package contains a SharePoint personal-storage path that includes organization and account identifiers.
- The workbook includes organization-specific wording in sheet labels and macro-generated email content.

### Findings in VBA source

- Three hard-coded email-related values are present in the Outlook section: recipient, CC, and sender-on-behalf address.
- Internal business-area wording is embedded in the email subject and body.
- The saved SAP variant is hard-coded.
- The local output path is hard-coded.

### What was not found

- No SAP password, Outlook password, or API key was found in the inspected VBA.
- No login form or credential-capture logic was found.
- The macro relies on already authenticated desktop sessions rather than storing credentials.

### Publication action

Use a sanitized copy for GitHub. Remove metadata, internal paths, organization-specific addresses, business names, production dates, and any report data containing suppliers, purchase orders, materials, pricing, or other confidential information.

## Current limitations

- No date validation or start/end-date relationship check.
- No explicit confirmation that SAP export completed successfully.
- No explicit file-existence check before attaching the report.
- Broad `On Error Resume Next` around SAP and Outlook setup can hide failures.
- First-child SAP connection/session selection may target the wrong session when multiple sessions are open.
- SAP control IDs may break when the SAP screen layout, transaction configuration, or saved variant changes.
- No retry, timeout, logging, or user-facing completion status is implemented.
- Email creation is skipped silently if Outlook object creation fails.
- Email recipients and message text are not configurable from the worksheet.

## Implemented versus suggested improvements

### Implemented

- Cell-based date input.
- Button-driven macro execution.
- SAP GUI report retrieval and export.
- Local file creation.
- Outlook draft creation with attachment.
- Manual review before sending.

### Suggested future improvements

- Create a protected configuration area for transaction, variant, output path, recipients, and template text.
- Add validation for blank, invalid, and reversed dates.
- Use structured error handling and an execution log.
- Verify output-file existence and report the result clearly.
- Replace the fixed `C:\TEMP` path with a configurable or user-specific temporary directory.
- Identify the intended SAP session explicitly.
- Add a test mode using synthetic or mocked data.
- Digitally sign the VBA project and document the trusted deployment process.
